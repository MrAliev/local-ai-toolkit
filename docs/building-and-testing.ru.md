Для проверки перед pull request используйте команду выше. Во время разработки быстрее
запускать отдельный тестовый проект:
`dotnet test tests/<name>/<name>.csproj --configuration Release`.

В Windows CI проверка Python SCIP включена в строгий режим. Закреплённый в каталоге
`@sourcegraph/scip-python@0.6.6` устанавливается в отдельный npm-каталог `scip-python-fixture`,
после чего запускается
`dotnet run --file scripts/quality/prepare-scip-python-fixture.cs --configuration Release -- <prefix>`.
Скрипт использует существующие проверки версии и SHA-256 всего bundle из установщика:
он не дублирует исправление и отказывается изменять неизвестный bundle. Два исправления
касаются разделителей путей Windows и выбора интерпретатора. Другие версии пакета требуют отдельной проверки.

На runner с Python 3.12 настоящие тесты проверяют переходы к определениям и ссылкам между
файлами, а также границы тел определений. Одного успешного `--version` недостаточно.
Отсутствие зависимостей или ошибка индексации приводят к падению CI; исключения для Python
из строгого режима больше нет.

Тест никогда не проверяет, насколько быстра машина: ждать надо наступления условия, а не
истечения срока — срок, в который может не уложиться корректный прогон, ничего не
доказывает, а в отчёте выглядит как поломка проверяемого кода.

## Независимые корпуса для проверки качества

Скрипт для разработчиков `scripts/quality/run.ps1` создаёт отдельные Git-репозитории C#,
TypeScript, Python и смешанный репозиторий. Запросы и эталонные ответы хранятся вне
индексируемых деревьев. Всего предусмотрено 70 поисковых проверок: 12/12/12/34. Смешанный
корпус повторяет вопросы отдельных языковых корпусов, поэтому это не 70 независимых вопросов.

Запускайте из корня репозитория в Windows. Нужны PowerShell 7.4+, Git с настроенным автором
коммитов, .NET 10 SDK и работающий брокер Local AI. Настроенная модель эмбеддингов и выбранная
модель OCR должны быть установлены и соответствовать политике размещения в памяти. Для
каждого запуска нужен каталог вывода вне репозитория — пустой или ещё не существующий. При сравнении длительностей
исключите одновременную работу других заданий брокера.

```powershell
dotnet build LocalAi.slnx --configuration Release
pwsh -NoProfile -File .\scripts\quality\test-runner.ps1

$qualityOutput = Join-Path (Split-Path -Parent (Get-Location).Path) ("LocalAi-quality-" + [Guid]::NewGuid().ToString("N"))

pwsh -NoProfile -File .\scripts\quality\run.ps1 `
  -OutputRoot $qualityOutput `
  -Mode All `
  -LocalAi .\src\LocalAi.Cli\bin\Release\net10.0\localai.exe `
  -CodeSearch .\src\CodeSearch.Cli\bin\Release\net10.0\codesearch.exe `
  -OcrModel glm-ocr:bf16
```

Режимы `Search` и `Ocr` запускают отдельные наборы проверок. `Prepare` создаёт поисковые
репозитории без вызовов моделей и не требует исполняемых файлов. Для каждого режима нужен
каталог вывода вне репозитория — пустой или ещё не существующий. В нём сохраняются результаты, исходные ответы и сведения о запуске.

### Сравнение на парном контрольном наборе

`-SearchSuite heldout-v2` добавляет поисковый набор: три новых репозитория исходников,
60 запросов EN/RU и 30 парных намерений. Для каждого языка предусмотрено по пять намерений
с ответом и без ответа. Эталоны подготовлены с помощью ИИ и до измерений проверены независимым
агентом, которому не показывали разметку и результаты поиска. Проверка человеком и новизна
относительно обучающих данных модели не подтверждены. После первого измерения набор считается
известным регрессионным корпусом.

Один раз выполните `-Mode Prepare -SearchSuite heldout-v2`. Проиндексируйте три репозитория
исходников через брокер, затем зафиксируйте в `heldout-v2/protocol.json` фактические Git-деревья,
хеши корпусов, идентификаторы поколений, все параметры поиска и профиль качества. Разметка
и результаты должны находиться вне исходных деревьев. Тег модели не подтверждает хеш весов
или серверную маршрутизацию; недоступные сведения остаются неизвестными.

Соберите baseline и candidate из чистых деревьев с записанными коммитами. До обоих поисковых
запусков сохраните отдельный artifact-plan JSON: `schemaVersion: 1`, `protocolSha256` зафиксированного
протокола и массивы `baseline.codeSearch` / `candidate.codeSearch`. Для исполняемого файла и всех
DLL рядом с ним нужны `file`, `version`, `recordedProductVersion` и `sha256`. Отдельный файл
исключает циклическую зависимость хеша сборки от протокола. Для обоих запусков
`-Mode Search -SearchSuite heldout-v2` передайте один `-PreparedRoot` и разные пустые `-OutputRoot`.
Повторного индексирования при этом нет. Runner проверяет все корпуса до поиска, сохраняет
вывод по мере поступления и после выполнения повторно проверяет исходники, разметку и сборки.

`dotnet run --file scripts/quality/evaluate-holdout.cs --configuration Release -- validate <protocol> <prepared-root>`
проверяет эталоны без поисковых запросов. Режим
`compare <protocol> <prepared-root> <artifact-plan> <baseline-root> <candidate-root> <report.json>`
требует совпадения зафиксированных идентификаторов и нормализованных последовательностей
исходных результатов. Проверяется совпадение поведения harness: ранжирование и порог `0.43`
не меняются, улучшение качества не заявляется. `test-heldout.ps1` проверяет данные и отказы
без retrieval; Windows CI запускает его и регрессионный тест потокового вывода процессов.

[Первый парный результат](https://github.com/MrAliev/local-ai-toolkit/tree/main/tests/CodeSearch.Tests/Fixtures/SearchEvaluation/heldout-v2/baseline-2026-11-18/README.ru.md)
сохраняет исходные строгие оценки и объясняет ограничение сопоставления символов TypeScript.
Протокол в репозитории явно помечен как каноническая копия, созданная после измерений. Для
нового запуска запишите свежие идентификаторы в отдельную копию и до измерений установите
`status: frozen-unmeasured`. Уже использованный набор нельзя представлять как новый слепой
контрольный корпус. Только дата калибровки профиля сравнивается по обозначенному моменту времени;
все остальные поля профиля должны совпадать точно.

Метрики запросов показываются по языкам исходников и запросов; отдельно считаются намерения,
для которых успешны обе формулировки, одна или ни одной. Результат на запрос без ответа означает
отсутствие размеченной прямой реализации: это операционное ложное срабатывание, не оценка
галлюцинаций. Синтетические шаблоны связаны между собой. Интервалы Уилсона для групп приведены
для справки при допущении независимости и не гарантируют качество на реальных репозиториях.
Длительности описывают конкретный запуск с общей нагрузкой брокера; неизвестное время ожидания
остаётся неизвестным. Исторические показатели v1 ниже получены на других данных.

Четыре эталона OCR содержат короткий и длинный текст EN/RU, в том числе повторяющиеся строки.
Повторы сохраняются при оценке. Отдельно рассчитываются доли ошибок символов и слов (CER/WER),
число непустых строк, полнота распознавания размеченных названий полей и точность их значений.
Техническое завершение CLI и полная длительность отделены от точности распознавания; время
очереди и выполнения, а также сведения об усечении сохраняются в исходных ответах, если
доступны. Недоступные показатели остаются неизвестными. Метрики полей не оценивают общее
понимание смысла.
