# Политика подписи кода

[English version](code-signing-policy.md)

**Статус: подключение планируется; одобрение SignPath и сертификат Authenticode не заявляются.**

Программы Local AI для Windows предполагается подписывать через бесплатную подпись кода SignPath
Foundation для проектов с открытым исходным кодом. **Пока в заметках к релизу не сказано, что
он подписан, его установщик не подписан Authenticode.** Сегодня релиз защищает его манифест:
он подписан ECDSA P-256, и установщик принимает пакет, только если манифест сходится с ключом,
встроенным в установщик, а пакет — с манифестом. См.
[«Что делает установщик»](how-it-works.ru.md#что-делает-установщик).

## Указание авторства

После одобрения подписанные через этот сервис релизы будут содержать строку:

Free code signing provided by [SignPath.io](https://signpath.io), certificate by
[SignPath Foundation](https://signpath.org).

## Что подписывается

Только программы, собранные из исходного кода этого репозитория собственной сборкой релиза
проекта:

| Файл | Что это |
| --- | --- |
| `LocalAi.Installer.exe` | установщик; он же удаляет Local AI |
| `localai-launcher.exe` | постоянная точка входа, на которую зарегистрированы все клиенты |
| `localai.exe` | командная строка |
| `codesearch.exe` | командная строка поиска по коду |
| `codesearch-mcp.exe` | сервер MCP поиска по коду |
| `locallm-mcp.exe` | сервер MCP локальных моделей |
| `LocalAi.Broker.exe` | брокер перед Ollama |

Файлы, которые проект не собирает, его сертификатом не подписываются никогда. В том числе
сторонние библиотеки в пакете: `pdfium.dll`, `libSkiaSharp.dll` и `libHarfBuzzSharp.dll`.

## Правила

- Запрос на подпись утверждает вручную утверждающий, по одному релизу за раз.
- На подпись отправляется только сборка коммита из `main`, сделанная из исходного кода
  сборкой релиза. Ничто, собранное на машине разработчика, не отправляется.
- Каждый участник команды пользуется многофакторной аутентификацией в GitHub и в SignPath.
- О программе, подписанной в нарушение этой политики, сообщается SignPath, а релиз, в котором
  она вышла, отзывается.

Это требования к будущему процессу подписи, а не подтверждение завершённого подключения
или проверки MFA. [Публикация и подпись](publication.ru.md) описывает оставшиеся шаги:
заявку, доверенную сборку CI, реальную политику сертификата и проверки продления сертификата.

## Подтверждения для релиза

Два workflow подтверждают разные факты в ограниченных пределах. Они не используют
рабочий ключ подписи, не публикуют релиз, не устанавливают кандидат и не закрывают
[issue 210](https://github.com/MrAliev/local-ai-toolkit/issues/210).

1. **`Build unsigned candidate`** собирает семь собственных программ для Windows из
   чистой копии выбранного коммита `main`. Манифест `localai.unsigned-candidate.v2`
   связывает коммит и дерево исходников, workflow/run/попытку, версию, платформу,
   размер и SHA-256 каждого файла. Задание сборки создаёт для манифеста аттестацию
   происхождения SLSA. Отдельное задание скачивает артефакт с точным ID, проверяет
   полный состав и все хеши, затем проверяет аттестацию с ожидаемыми репозиторием,
   SHA исходников, workflow и SHA подписанта, веткой, типом утверждения и runner
   GitHub. Контрольные проверки с чужими исходниками и другим workflow должны
   завершиться отказом. Кандидат принимается, только когда **оба задания именно
   этого запуска успешны**. Сохраните исходный коммит, run/попытку, ID и digest
   артефакта, манифест и результат проверки. Одной загрузки артефакта недостаточно.
2. **`Attest release assets`** скачивает четыре поддерживаемых файла уже
   опубликованного релиза по числовым ID релиза и файлов. Проверяет имена, размеры
   и доступные хеши API, затем повторно читает метаданные релиза, чтобы обнаружить
   замену во время скачивания. Аттестация типа `release-asset-receipt/v1` фиксирует
   полученные хеши и идентификаторы релиза и запуска. Поля
   `sourceBuildVerified=false` и `authenticodeVerified=false` явно означают: workflow
   скачал эти файлы, но не собирал их. Последующая проверка с ожидаемым workflow
   позволяет обнаружить другие байты, однако такая запись не удостоверяет
   первоначального издателя и не исключает подмену до момента фиксации.

Перед следующим релизом убедитесь, что оба workflow **активны** в GitHub и кандидат
из точного коммита прошёл задание проверки. Отключённый workflow, отсутствие запуска,
ошибка или незавершённая проверка не позволяют пройти этот этап приёмки. После
публикации запустите фиксацию файлов релиза и сохраните успешные проверки всех
четырёх файлов. Для старого релиза запускайте workflow вручную на `main` с числовым
ID релиза. Поздняя фиксация не является подтверждением исторической сборки.
Для прежних релизов прохождение проверки кандидата задним числом не заявляется.

Для проверки скачанного кандидата используйте скрипт из того же проверенного
коммита и установленный доверенный GitHub CLI с выполненным входом:

```powershell
./scripts/verify-localai-unsigned-candidate.ps1 -ArtifactRoot <downloaded-folder> `
  -ExpectedSource <commit> -ExpectedVersion <version> -ExpectedRunId <run-id> `
  -ExpectedRunAttempt <attempt> -EvidencePath <outside-artifact>/verified-candidate.json
```

Ожидаемые значения берите из проверенного запуска, а не из скачанного манифеста.
Эти проверки относятся к файлам кандидата или полученным файлам релиза. Они не
подтверждают версию, установленную или запущенную на конкретном компьютере.
Рабочая подпись, хранение ключей, ECDSA-подпись манифеста пакета и проверка
установки и работающей версии остаются отдельными условиями приёмки. Issue 210
остаётся открытой.

Используются механизмы [действия аттестации](https://github.com/actions/attest)
и [проверки GitHub CLI](https://cli.github.com/manual/gh_attestation_verify).
