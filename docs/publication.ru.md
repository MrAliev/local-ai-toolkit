# Проверки публикации и подписи

[English version](publication.md)

Это инструкция сопровождающего по открытию репозитория и публикации документации.
Невыполненный шаг не считается доказательством. Существующая задача по подписи:
[#210](https://github.com/MrAliev/local-ai-toolkit/issues/210).

## До изменения видимости репозитория

1. Проверьте публикуемый коммит и все открываемые удалённые ветки/теги. Сканер секретов
   должен скрывать значения и сначала обнаружить положительный искусственный пример.
   Записывайте правило, путь, ревизию и классификацию, но не значение секрета.
2. Проверьте данные вне Git: доступные журналы и артефакты Actions, тексты и комментарии
   issues/PR, ревью, release notes/assets и вложения. Отметьте недоступные и непроверенные
   поверхности; отсутствие срабатываний не гарантирует отсутствия секретов.
3. Подтвердите права на код проекта и MIT-лицензию. Сохраните уведомления об авторских
   правах и лицензиях зависимостей. У весов моделей и отдельно скачиваемых зависимостей
   собственные лицензии; репозиторий не меняет их на MIT.
4. Проверьте парные документы, полный набор тестов и CI для конкретного публикуемого коммита.
   Описание конфиденциальности должно отражать соединения, а подписи — не преувеличиваться.
5. Разберите срабатывания до открытия истории, журналов и обсуждений. Исправление текущего
   файла не удаляет ключ из истории. Сначала отзовите раскрытые учётные данные, затем
   рассматривайте очистку истории; не переписывайте общую историю незаметно.

## Публикация документации

Портал — `docs/index.html`; справочник генерируется из парных README. Workflow
**Documentation** собирает Jekyll-сайт в PR. Развёртывание разрешено только из публичного
`main`; приватные сборки и PR не должны публиковать сайт.

После проверки раскрытия включите GitHub Pages с источником **GitHub Actions**, Wiki
и опубликуйте её версионируемые исходники через `scripts/publish-wiki.ps1`.
Сначала нужно инициализировать Git-репозиторий Wiki, создав Home на GitHub.
Разрешите редактирование только участникам с доступом к репозиторию.

```powershell
./scripts/publish-wiki.ps1 -PreviewDirectory C:\work\localai-wiki-preview
# Проверьте страницы до публикации конкретного проверенного коммита:
./scripts/publish-wiki.ps1 -Publish
```

После успешного развёртывания укажите homepage `https://mraliev.github.io/local-ai-toolkit/`.
Проверьте оба языка, мобильный вид, навигацию, схемы, крайние случаи калькулятора и клавиатуру.
Включите private vulnerability reporting до того, как публичная политика отправит туда
пользователей; включите secret scanning/push protection и предупреждения зависимостей,
где они доступны. Подтвердите фактические настройки через API/UI.

## Бесплатная Authenticode-подпись через SignPath Foundation

[Официальная заявка](https://signpath.org/apply.html) предполагает публичный, поддерживаемый
проект с релизом и проверку по [действующим условиям](https://signpath.org/terms).
Одобрение не гарантируется. Сертификат принадлежит SignPath Foundation, ключ хранится
у сервиса; это не скачиваемый приватный ключ, выданный сопровождающему.

Подготовьте поля по проверенным публичным сведениям:

| Поле | Значение |
| --- | --- |
| Проект | Local AI Toolkit |
| Репозиторий | https://github.com/MrAliev/local-ai-toolkit |
| Homepage | https://mraliev.github.io/local-ai-toolkit/ после развёртывания |
| Загрузки | https://github.com/MrAliev/local-ai-toolkit/releases |
| Privacy | Опубликованная страница конфиденциальности |
| Категория | Инструменты разработчика, если есть в форме |
| Сопровождение | Индивидуальный проект @MrAliev |
| Сборка | GitHub Actions; отличайте кандидатов CI от прежних локальных релизных сборок |
| Репутация | Реальная история релизов, CI и ревью; не выдумывайте пользователей или популярность |
| Контакт | Подтверждённые владельцем имя и email, переданные приватно |

Владелец должен подтвердить обработку персональных данных и обязательные условия заявки.
Не предполагаются включённая MFA, одобрение аккаунта, subject сертификата или fingerprint
ключа. Переписка по заявке и API-токены остаются вне репозитория.

## После одобрения SignPath

1. Настройте trusted GitHub builds, конфигурацию только собственных PE-файлов,
   ограничения product/version и сопровождающего с MFA, одобряющего релиз.
2. Закрепите проверенные actions; вся доверенная цепочка собирается на GitHub-hosted
   runners. Не передавайте секреты подписи недоверенному коду PR. Кандидат сборки — не релиз.
3. Соберите и загрузите артефакт в этом workflow; запросите подпись по его artifact ID.
   Каждый запрос требует ручного одобрения. Слияние зелёного PR не одобряет подпись.
4. Проверьте каждую полученную подпись и timestamp по реальному сертификату. Согласованно
   замените subject/SPKI-заглушки во всех проверках только после получения этих данных.
5. Подпишите собственные программы **до** создания итогового пакета. Не подписывайте
   своим сертификатом чужие DLL. Вычислите хеш итогового ZIP, подпишите манифест и проверьте
   дистрибутив. После вычисления хеша/подписи пакет изменять нельзя.
6. Проверьте переход старого клиента на новый релиз, чужого издателя, изменённый пакет,
   отзыв/timestamp и обновление сертификата. Проверка одного SPKI требует явного плана
   ротации; добавление второй подписи само по себе не доказывает совместимость.
7. Включайте `RequiresAuthenticode` только с реальной политикой и успешными интеграционными
   проверками. Опубликуйте издателя, инструкции проверки и независимые доказательства
   digest/provenance. Закрывайте #210 только по данным фактического релиза и хранения ключей.

Существующая аттестация assets фиксирует загруженные байты. Её нельзя описывать как
provenance сборки из исходников, пока такую аттестацию не создаёт сама сборка.

[Неподписанный кандидат](unsigned-release-candidate.ru.md) описывает основу CI
и её ограничения. Результат не является устанавливаемым подписанным дистрибутивом.
