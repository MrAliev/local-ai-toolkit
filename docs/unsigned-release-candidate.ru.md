# Неподписанный кандидат релиза

[English version](unsigned-release-candidate.md)

Workflow **Build unsigned candidate** в GitHub Actions готовит сборку для проверки.
Он не подписывает файлы Authenticode, не создаёт устанавливаемый релиз, не подписывает
манифест и не публикует релиз GitHub. Неподписанный кандидат нельзя использовать как
источник обновления или представлять как подписанный дистрибутив. Для будущей интеграции
подписи ещё нужны одобрение SignPath и настоящий сертификат.

## Сборка и проверка кандидата

После попадания workflow в `main` сопровождающий может открыть **Actions → Build unsigned
candidate → Run workflow**, выбрать `main` и ввести нужную версию, например `0.3.0-rc.1`.
Эквивалентная команда:

```powershell
gh workflow run build-unsigned-candidate.yml --repo MrAliev/local-ai-toolkit --ref main -f version=0.3.0-rc.1
```

Задание запускается только вручную в `MrAliev/local-ai-toolkit` для `refs/heads/main`.
Checkout использует неизменяемый `github.sha`, выбранный при запуске, а не версию или
произвольную ссылку на исходники из входных параметров. Последующее изменение `main`
не меняет исходники этого запуска. Скрипт повторно проверяет репозиторий, событие,
ветку и SHA рабочего дерева до компиляции. Версия содержит три числовые части не более
65534 каждая, необязательную prerelease-часть SemVer и не содержит build metadata.

Вся компиляция выполняется на GitHub-hosted runner `windows-2025` с SDK из `global.json`.
Workflow имеет только `contents: read`, отключает сохранение учётных данных checkout
и фиксирует три actions по commit ID. В нём нет учётных данных для подписи, прав
публикации релизов, произвольных команд или обработчиков после сборки из параметров
запуска. Скрипт отказывается перезаписывать существующий каталог кандидата.

Успешный запуск загружает один артефакт с SHA исходников, ID запуска и номером попытки
в имени. В сводке сохраняются GitHub artifact ID и digest. Артефакты хранятся семь дней.
При ошибке сборки или проверки частичный кандидат не загружается. Архив содержит
только следующие собственные бинарные файлы в `own-pe/`:

- `codesearch.exe`
- `codesearch-mcp.exe`
- `locallm-mcp.exe`
- `localai.exe`
- `localai-launcher.exe`
- `LocalAi.Broker.exe`
- `LocalAi.Installer.exe`

Каждый файл должен иметь статус Authenticode `NotSigned`. Отдельные сторонние библиотеки
и неожиданные исполняемые файлы не попадают в загружаемый артефакт. Восьмой файл,
`unsigned-candidate.json`, содержит `signed: false`, версию, SHA исходников, ссылку на
запуск, длину и SHA-256 каждого бинарного файла. Хеши описывают байты; эти метаданные
не являются подписью или независимым доказательством происхождения сборки. Проверяйте
сам запуск GitHub и его коммит вместе со скачанными файлами.

## Что нужно до подписи и публикации

Интеграция SignPath с GitHub проверяет происхождение сборки и загруженный артефакт
GitHub; для OSS-сервиса все задания до запроса подписи должны выполняться на
GitHub-hosted runners. В дальнейшем отправку нужно добавить в доверенный workflow,
передавая настоящий artifact ID шага загрузки. Скачивание и повторная загрузка файлов
через посторонний workflow эту интеграцию не заменяют. GitHub упаковывает артефакт в ZIP,
поэтому будущая конфигурация SignPath должна соответствовать архиву и явно выбирать
семь собственных PE-файлов. Нельзя подписывать сторонние DLL от имени проекта.
[Интеграция SignPath с GitHub](https://docs.signpath.io/trusted-build-systems/github),
[условия SignPath Foundation](https://signpath.org/terms).

Оставшиеся этапы релиза требуют отдельных проверок:

1. Получить одобрение OSS-проекта, настроить реальные ID проекта и политики, согласовать
   с SignPath удостоверяемого издателя и метаданные бинарных файлов. Настроить ограничения
   происхождения и ручное одобрение подписи: Foundation требует одобрять каждый релиз.
   Нельзя принимать условия за сопровождающего или выдумывать выданный сертификат.
   [Условия SignPath Foundation](https://signpath.org/terms).
2. Добавить настоящую интеграцию подписи в проверенный workflow и отдельно сохранить
   полный runtime payload той же сборки. Сторонние файлы оставить неизменными и вне
   выбора для подписи. После одобрения проверить возвращённые подписи всех семи
   собственных PE-файлов и заменить в payload только их.
3. Настроить установщик и проверку на настоящий subject сертификата и закреплённый
   публичный ключ. Проверить первую установку, обновление, отказ при подмене и
   совместимость сертификатов. Несуществующий сертификат этот этап пройти не может.
4. Упаковать payload после Authenticode-подписи, затем сформировать окончательные хеши
   и подписанный ECDSA манифест с отдельно защищённым ключом релизов. Не помещать этот
   приватный ключ в workflow кандидата. Публиковать только после успешной проверки
   пакета и установщика. Последующая переупаковка или изменение PE-файлов нарушит
   соответствие ранее рассчитанным хешам или подписям.

Существующий workflow аттестации опубликованных файлов фиксирует скачанные assets
релиза, но не устанавливает, что они получены из этой сборки кандидата. Ни он,
ни неподписанный артефакт не закрывают оставшееся требование Authenticode.
